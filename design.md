# Дизайн Omni

Omni — рабочее пространство преподавателя: выбор занятия, посещаемость, оценки,
материалы и проверка работ. Главная ценность — быстро понять контекст и безопасно
выполнить действие. Направление уже задано: спокойный светлый интерфейс, плотные
таблицы, Golos Text, фиолетовый акцент, тонкие разделители. Сохраняем его; три новых
концепции сейчас не нужны. Для другого продукта направление выбирается заново.

## Фактическая архитектура

React 19 + strict TypeScript + Vite 6; lucide-react для функциональных иконок,
нативные dialog и form-контролы, Playwright для браузера. Tailwind, компонентного
UI-kit и библиотеки анимации нет; добавлять их ради процесса не требуется.

- `src/app` — композиция и shell, `src/features` — предметные экраны,
  `src/components` — общие элементы. `src/demo` — отдельный пример, не доказательство
  поведения live-компонентов. Визуальная проверка использует настоящий Workspace.
- `src/styles/styles.css` — базовые стили и legacy/demo, `theme.css` — тема root/host,
  `src/app/live.css`, `workspace.css` — рабочие экраны; локальные feature CSS и
  `components/data/table.css` дополняют каскад. Это существующая система, не единый
  формализованный UI-kit. Есть повторяющиеся значения и высокоспецифичные селекторы.
- Расширение вставляет CSS через `src/app/extension/extension-entry.tsx` в Shadow DOM.
  Новый CSS должен попасть в этот список; одного web-preview недостаточно.
- Общие паттерны: DataTable, TableBulkEditor, HelpTip, SearchableSelect, DatePickerPopover,
  StudentAvatar, AverageGrade. Изменения общего компонента проверять у потребителей.

## Токены: текущие значения и правила использования

Источники истины — CSS, а не эта таблица. Здесь зафиксированы базовые alias и
роль; component fallbacks и live overrides могут отличаться. Не заменять всё
глобально без проверки каскада и dark theme.

| Роль | Light | Dark (theme.css) |
| --- | --- | --- |
| Фон `--bg` | #f7f8fc | #13151d |
| Поверхность `--surface` | #ffffff | #1c1f2a |
| Текст `--text` | #172033 | #edf0f7 |
| Вторичный `--muted` | #737b8d | #adb4c6 |
| Граница `--border` | #e5e8f0 (live также #e7e9f2) | #3a4051 |
| Акцент `--purple` | #6d55d8 | #c2adff (текст; заливка #7956d5) |

Dark palette определяет semantic `--omni-*` и переназначает старые alias. Успех,
ошибка и предупреждение используют соответствующие semantic цвета с текстом или
иконкой, не только цвет. Не использовать `--purple` как универсальную заливку в dark.

Golos Text, sans-serif fallback; базовый host 13px, вес 400. Практический диапазон
существующего UI — примерно 9–24px. Малые 9–11px надписи — предмет аудита, а не
образец для новых значимых действий. Для новых форм ориентир 13–14px, вторичного
текста 12px, заголовков 16–24px с понятной иерархией; проверить плотность и zoom.

Для нового кода предпочитать шаги отступов 4/8/12/16/24/32px и радиусы 6–8px
контролов, 12–15px диалогов/крупных поверхностей. Это нормализация существующих
значений, ещё не новые CSS-переменные. Сначала переиспользовать локальные паттерны.
Тень служит отделению overlay, не обрамлению каждого блока.

## Композиция и взаимодействия

Рабочая область первична, контекст урока и навигация вторичны. Один доминирующий
акцент действия; destructive/overwrite требуют ясного обозначения. Не повторять
счётчики и инструкции рядом. Подробности — через HelpTip, раскрытие или справочник;
ошибки и последствия не прятать в hover. Иконка должна помогать опознать действие,
иметь доступное имя. У карточки должна быть смысловая граница или взаимодействие.

Не добавлять декоративные градиенты, stock-фото, hero, случайную анимацию и пустые
поля ради «премиальности». В существующем UI есть legacy карточки/градиенты: аудит
оценивает их пользу, а не требует массового удаления. Плотность не оправдывает
нечитаемость. На mobile таблица может скроллиться внутри своей области; страница,
диалоги и основные действия должны оставаться доступны.

Breakpoints сейчас неоднородны: 500/760/900/1050/1200/1500px и локальные значения.
Не унифицировать их механически. Проверять минимум 1440×1000, 820×1180 и 390×844,
а при изменении breakpoint — обе его стороны. Цветовые темы, 200% zoom, длинные
имена/пустые данные проверять при влиянии изменения на них.

Focus должен быть видимым; Tab/Shift+Tab, Escape, возврат фокуса, контраст, размеры
целей и touch проверяются отдельно. Motion — короткое объяснение изменения
состояния; уважать prefers-reduced-motion. Не добавлять motion library без причины.

## Воспроизводимый процесс

1. **Анализ:** пользовательская задача, реальная страница/данные, ограничения,
   состояния, критерии приёмки и потребители компонентов. Малый фикс — короткий цикл.
2. **Референсы:** сначала текущие лучшие экраны/компоненты Omni и реальные
   сценарии преподавателя. Внешние референсы выбирать по сопоставимой задаче;
   записать источник и конкретный полезный принцип, не копировать стиль целиком.
3. **Арт-дирекшен:** до существенного UI написать три коротких тезиса: визуальное
   направление, иерархия контента/действий, характер взаимодействий. Для Omni это
   рабочая поверхность → контекст → действие, а не hero → маркетинговый CTA.
4. **Дизайн-система:** выбрать существующие tokens/components, размеры, состояния,
   responsive-поведение. Новые решения добавлять только при реальном пробеле.
5. **Реализация:** соблюдать границы слоёв, функциональные проверки и explicit Save.
6. **Визуальный аудит:** открыть реальный браузер; посмотреть снимки и состояния,
   оценить композицию, типографику, плотность, иерархию, выравнивание, контраст,
   доступность и пользу каждой детали. PASS кода не равен качественному дизайну.
7. **Исправления:** сначала блокирующие дефекты, затем иерархия/читаемость и polish;
   повторить только затронутые проверки. Записать оставшиеся проблемы и ограничения.

## Команды и доказательства

Установка окружения: `npm ci`, затем `npx playwright install chromium` на чистой
машине. Node 24 как в CI. Не переустанавливать рабочие зависимости без причины.

`npm run test:visual` — одна команда: TypeScript + extension build + Playwright
Chromium с отдельным временным профилем и вымышленными API fixtures. Открывает
настоящий интерфейс расширения, не demo. Реальной сессии/академических записей нет.
Закрывает браузер и удаляет временный профиль; снимки остаются в ignored tmp.

Результаты:
- `tmp/visual-audit/index.html` — галерея; открыть локально в браузере.
- `tmp/visual-audit/*.png` — default (начало страницы; внутренний scroll-контейнер не разворачивается в fullPage), workspace (таблица), focus, hover, empty, selected, settings,
  invalid на desktop/tablet/mobile. Disabled виден в default/invalid.
- `tmp/visual-audit/run-status.json` — running/passed/failed с временем запуска. Перед сборкой старый отчёт удаляется, галерея помечается незавершённой; старые PNG не доказывают успешность нового запуска.
- `tmp/visual-audit/report.json` — viewport/state, версия браузера, overflow и
  примеры малого текста. Это диагностические сигналы, не автоматический UX-вердикт.

Просмотреть минимум все default и изменённые состояния через браузер/view_image.
Галерея и исходные PNG обязательны для ручной оценки. Скрипт проверяет containment,
фокус и отсутствие записей, но не утверждает соответствие WCAG или качество вкуса.
Нет pixel-baseline: утверждать его можно только после осмысленного просмотра.
Стабилизированы fixture/ожидание данных/анимации; дата, ОС, шрифты и Chromium могут
влиять на снимки. Google Fonts в fixture блокируются: fallback отличается от
production Golos Text. Для точной типографики отдельно проверить доступный шрифт;
не считать pixel diffs между разными средами дефектом продукта.

Для новой страницы расширить соответствующий fixture/ветку `tests/extension-browser.mjs`
и матрицу состояний. Не считать аудит урока покрытием всего продукта. Loading/error
транспорта, успешный draft/Save, stale/context и частичные подтверждения проверяются
существующими feature/extension browser tests по VERIFICATION.md. Для чисто
визуального изменения полный auth/Save сценарий повторять не требуется.

Матрица значимой UI-задачи: default + empty/loading/error + hover/focus +
selected/expanded/modal + disabled/invalid + success, только применимые состояния.
В audit-заметке отметить PASS/FAIL/NOT RUN по каждой важной проверке, ссылки на
снимки, severity, конкретный дефект и предложение. Screenshots с реальными PII
не сохранять в git. Пример результата — [пробный аудит](docs/design-audit-lesson.md).
