## Как выполнять это ТЗ

**Не реализовывать весь документ за один заход.** Это очередь отдельных задач.
Пользователь указывает номер этапа. Если передан только документ без номера,
выполнить этап 0: анализ и предложение решений, без изменения продуктового кода.
После выбранного этапа сообщить результат, фактические проверки и оставшиеся
вопросы. Следующий этап автоматически не начинать. Каждый этап должен оставлять
работающее приложение и иметь самостоятельный результат для проверки.

Прочитать актуальный `AGENTS.md`. Для нетривиальной разработки использовать
`omni-workflow`, проверки выбирать по `.codex/engineering/VERIFICATION.md`.
Изменения публичных контрактов и поведения академических записей проводить
по обязательным маршрутам проекта, включая план и независимое ревью там,
где это требуется. Этот документ не отменяет эти правила.

изменение снимка или контекста делает его недействительным. Применение — только

## Контекст и цель

Приложение — Chromium MV3, React 19, strict TypeScript, Vite 6, npm.
Основной экран первого внедрения — «Мой урок».

Пользователь считает нынешний интерфейс недостаточно универсальным и слишком
расточительным по постоянному месту на экране. Вместо добавления отдельной
кнопки под каждый сценарий нужны общие инструменты:

1. Удобная панель настройки таблицы: произвольная цепочка сортировок и фильтры.
2. Процедурное заполнение ячеек на основе значений и агрегатов таблицы.
3. Компактные действия в существующих карточках; подробные настройки и
   вспомогательные сценарии открываются в модальных окнах.

Пример пользовательского сценария: вычислить среднее по средним оценкам
учеников и выставить результат в «Оценки за урок». Это отличается от другого,
уже реализованного сценария: округлить вверх индивидуальную среднюю каждого
ученика и поставить каждому его собственный результат.

- Глубина вложенности групп И/ИЛИ, сохранённые представления, хранение настроек
  между сессиями, настройка видимости/порядка столбцов.
- Правила округления агрегатов, обработки отсутствующих значений, перезаписи
  заполненных оценок и область вычисления по умолчанию.

Эти пункты не считать молча одобренными дополнительными функциями. Предложить
конкретные значения по умолчанию и согласовать только существенные развилки.

## Общие требования

- Данные и действия только реальные, доступные через существующую интеграцию.
  Не создавать фиктивные API, метрики или серверные возможности.
- Вычисления работают с типизированными значениями полей, не с текстом JSX.
- Порядок представления: исходные данные с текущим черновиком → фильтрация →
  сортировка → пагинация. Страница — только способ отображения, не область
  агрегирования или массовой записи.
- Области «выбранные», «все по фильтру», «вся группа» явно различаются.
  Для каждого действия показывать число затрагиваемых строк.
- Сортировка и пагинация не меняют идентичность выбранных учеников. Правило
  изменения выбора при смене фильтра определить явно; скрытые строки не должны
  незаметно получать изменения. Смена аккаунта/урока сбрасывает старые цели.
- Все новые действия урока меняют локальный черновик. Отправка через существующее
  явное «Сохранить», с проверками аккаунта, контекста, исходных значений и readback.
  Не добавлять автоматические повторы неопределённых записей.
- Расчёт операции выполняется по одному снимку исходных данных. Заполнение
  первых строк не должно менять агрегат для следующих строк той же операции.
- Неприменимые строки и причины показывать явно. Не пропускать их молча.
- Общие компоненты должны сохранить работу остальных потребителей. Не переводить
  все страницы на новый интерфейс без отдельной задачи.
- Модальные окна: управление клавиатурой, Escape, фокус внутри окна и возврат к
  открывшей кнопке, доступные названия и адаптация к узкому экрану. Использовать
  существующие компоненты/стили проекта; учитывать Shadow DOM расширения.
- Не выполнять живые академические записи, публикацию или релиз в рамках ТЗ.

## Этап 1. Панель настройки и цепочки сортировки

Добавить компактный вход в настройки таблицы урока. Внутри — список критериев
сортировки: поле, направление, приоритет; добавление, удаление, изменение порядка.
Перетаскивание, если используется, дополнить кнопками для клавиатуры.

Использовать типы значений, стабильную сортировку и определённое положение пустых
значений. Числа сортируются как числа, русские имена — как текст с локалью.
В интерфейсе видны активность настроек и способ их сбросить. Сортировка по
заголовкам, если остаётся, должна согласованно менять ту же модель состояния.

Приёмка: несколько критериев реально применяются ко всей выборке до пагинации;
изменение приоритетов меняет порядок ожидаемо; равенства и пустые значения
детерминированы; выбор строк и действия привязаны к ID, не индексам.
Проверки: целевые unit-тесты и браузерное управление панелью, сборка по маршруту
проекта; регрессии изменённых потребителей общего DataTable.

## Этап 2. Конструктор фильтров

В той же панели добавить произвольное число условий по доступным полям.
Операторы зависят от типа: текст, число, перечисление/статус, заполненность;
даты и булевы поля — только там, где они действительно имеются.
Поддержку И/ИЛИ и вложенности реализовать в согласованном на этапе 0 объёме.

Должны выражаться: «присутствует И оценка пуста», диапазон средней,
«присутствует ИЛИ опоздал». Предусмотреть редактирование, удаление и сброс условий,
объяснение некорректных значений и состояние пустой выборки.

Приёмка: фильтры работают по всем строкам, согласованы с поиском, сортировкой,
счётчиками и массовыми действиями. `0` и `false` не считаются отсутствием данных.
После фильтрации страница остаётся допустимой. Нет скрытых изменений учеников
вне заявленной области действия.
Проверки: комбинации условий, границы числовых диапазонов, пустые данные,
изменение выбора при фильтрации; браузерная проверка цепочки фильтр → действие.

## Этап 3. Процедурные значения

Сделать единый механизм заполнения, отделив целевой столбец от способа получения
значения. Убрать необходимость создавать отдельный псевдостолбец под каждый
алгоритм (сейчас есть «Работа на уроке · средняя ↑»).

Минимальные операции:
1. Одинаковое введённое значение.
2. Значение поля текущего ученика с выбранным округлением — сохранить существующий
   сценарий индивидуальной средней с округлением вверх.
3. Среднее арифметическое поля по явно выбранной области строк, затем применение
   результата к явно указанным получателям.

Пример приёмки: средние 8, 10, 11 → среднее 29/3 → округление вверх → оценка 10
каждому получателю. В индивидуальном режиме эти же ученики получают 8, 10, 11.

До применения показать источник, область расчёта, получателей, округление,
изменения «было → станет» и причины невозможности расчёта. Установить явную
политику пустых значений и перезаписи. При изменении исходных данных предварительный
результат должен обновиться либо стать недействительным до нового расчёта.

Вычисления не должны зависеть от сортировки/страницы, выдавать NaN/Infinity,
нарушать допустимую шкалу или частично изменять черновик при ошибке проверки.
Не использовать `eval`, `Function` или исполнение пользовательского JavaScript.
Произвольный язык формул — отдельная задача, если он будет выбран.

Проверки: индивидуальный и агрегатный режимы, запятая/точка в исходных данных,
пустые/невалидные значения, устаревший контекст, исходные оценки, отсутствие
записей до Save. Проверить существующий путь сохранения и отрицательные сценарии
по правилам академических мутаций проекта.

## Этап 4. Компактное распределение топкойнов

Убрать постоянный большой блок из потока страницы. Разместить над таблицей
основную кнопку «Распределить топкойны» и шестерёнку с доступным названием
«Настройки распределения топкойнов».

Шестерёнка открывает модальное окно с текущими параметрами алгоритма и понятным
описанием. Основная кнопка сразу рассчитывает и применяет результат к черновику
по актуальным данным и настроенным параметрам. Это не отправка в Omni.
Область действия должна быть видна и соответствовать решению этапа 0.

Сохранить существующие ограничения присутствия, бюджета всего урока, шкалы,
ручных изменений и режима замены наград. Скрытые фильтрами строки всё равно
учитываются в общем бюджете. Не менять формулу распределения ради переноса UI.
При невозможности применения показывать причину рядом с действием.
Хранение параметров между сессиями и отмена последней операции — только в
согласованном объёме; не придумывать новый общий storage-контракт молча.

Приёмка: обычное распределение занимает одно действие; настройки доступны
отдельно; место большого блока освобождено; бюджет и сохранение не регрессируют.
Проверки: текущие тесты алгоритма, быстрый запуск, изменение параметров, блокировки,
узкий экран, клавиатура и фактический интерфейс расширения.

## Этап 5. Копирование прошлого урока в модальном окне

Разместить кнопку «Скопировать с прошлой пары» в `lesson-context`. Отдельную
постоянную карточку копирования убрать. По кнопке открывать существующий сценарий
в модальном окне: дата/пара, загрузка, выбор переносимых данных, предварительный
результат, режим замены заполненных значений, применение к черновику.

Сохранить сопоставление по ID, ограничения источника, проверки актуальности,
обработку ошибок, бюджет наград и явное Save. Закрытие без применения не меняет
черновик. Смена урока/аккаунта не позволяет применить результат старого окна.
Не добавлять автоматическое копирование или отправку при открытии окна.

Приёмка: весь прежний сценарий доступен из lesson-context, большой блок исчез,
повторное открытие и закрытие работают предсказуемо, фокус возвращается к кнопке.
Проверки: перенос пустых/заполненных значений, отмена, ошибка загрузки, смена
контекста, браузерный проход и регрессии lesson-copy/lesson-draft.
