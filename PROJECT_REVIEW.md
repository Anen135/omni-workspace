# Отчёт о состоянии Omni Workspace

Дата: 30 сентября 2026 года. Проверенный коммит: `006838e`. Версия: `0.3.0-beta.1`.

**Обновление:** замечание P1 исправлено после ревью. При смене аккаунта или преподавателя расширение обновляет версию сессии; другие вкладки очищают старые данные и загружают актуальные. Добавлена регрессия с двумя вкладками в `tests/extension-browser.mjs`. Остальные замечания ниже сохраняют исходный статус.

**Вывод:** проект имеет рабочую основу для ограниченного бета-тестирования: сборка проходит, основные пользовательские сценарии покрыты проверками, границы доступа расширения продуманы. Для стабильного выпуска необходимо устранить рассинхронизацию аккаунтов между вкладками, сломанную навигацию и недостаточную устойчивость к ошибкам API и конкурирующим запросам. Полную готовность к эксплуатации на основании этого ревью подтвердить нельзя.

## Объём и методика

Изучены React/TypeScript-интерфейс, Manifest V3 и обработчик команд, общий адаптер Omni, локальный сервер, исходники desktop-оболочки, тесты, сборка и GitHub Actions. Выполнены модульные и браузерные проверки, сборка расширения, аудит npm-зависимостей и дополнительные воспроизведения на вымышленных данных.

Реальный аккаунт Omni не использовался. Локальные профили браузера и личные выгрузки не исследовались. Desktop-приложение не собиралось и не запускалось: замечания к нему основаны на исходниках. Совместимость с минимальной заявленной версией Chrome 120 и всеми версиями Edge/Opera не проверялась. Исходный код проекта не изменён; диагностические сценарии находятся в игнорируемом каталоге `tmp/`.

## Замечания по приоритету

### 1. P1 — смена аккаунта не очищает данные в остальных вкладках расширения

**Места:** [extension/background.mjs:22](extension/background.mjs#L22), [src/LiveWorkspace.tsx:104](src/LiveWorkspace.tsx#L104), [src/LiveWorkspace.tsx:130](src/LiveWorkspace.tsx#L130).

Каждое нажатие значка расширения создаёт новую вкладку интерфейса. Смена аккаунта или преподавателя очищает состояние только инициировавшего её компонента. Остальные вкладки не получают уведомлений; регулярная проверка состояния работает только во время ожидания входа.

**Воспроизведено в Chromium:** после перехода на аккаунт `3` первая вкладка показала новый аккаунт, а вторая продолжила показывать аккаунт `2` и статус «Подключено». Старые сведения остаются видимыми и доступными для экспорта до следующего обновления или запроса. Это проблема согласованности и конфиденциальности локально отображаемых данных, а не доказательство обхода авторизации сервера.

**Рекомендация:** ввести общую версию сессии и уведомлять все вкладки при смене аккаунта/преподавателя. При уведомлении очищать снимки, карточки и материалы; ответы предыдущей версии сессии игнорировать. Дополнительно проверять актуальность аккаунта при возвращении фокуса. Зафиксировать сценарий двух вкладок в регрессионном тесте.

### 2. P2 — нажатие логотипа ломает страницу расширения

**Места:** [src/LiveWorkspace.tsx:192](src/LiveWorkspace.tsx#L192), [extension/policy.mjs:9](extension/policy.mjs#L9).

Ссылка логотипа имеет `href="/"`. В расширении это переход на корень `chrome-extension://<id>/`, тогда как входная страница — `/index.html`.

**Воспроизведено:** нажатие логотипа привело к `chrome-error://chromewebdata/` и `ERR_FILE_NOT_FOUND`. Дополнительно политика сообщений допускает именно `/index.html`, поэтому простое разрешение загрузки корня не решит весь контракт навигации.

**Рекомендация:** использовать явный адрес входной страницы, учитывающий среду исполнения, либо кнопку возврата к начальному разделу без перезагрузки. Проверять навигацию в собранном расширении.

### 3. P2 — некорректный часовой пояс из API полностью обрушает интерфейс

**Места:** [src/LiveWorkspace.tsx:54](src/LiveWorkspace.tsx#L54), [desktop/omni-agent.mjs:37](desktop/omni-agent.mjs#L37), [src/main.tsx:129](src/main.tsx#L129).

Поле `timezone_name` передаётся в `Intl.DateTimeFormat` без проверки. Подстановка `Europe/Moscow` защищает только от пустого значения. Непустая неподдерживаемая строка вызывает исключение непосредственно при рендеринге. Границы обработки ошибок React нет.

**Воспроизведено через UI:** ответ с `timezone: 'Invalid/Zone'` дал ошибку `Invalid time zone specified: Invalid/Zone`; содержимое `#root` стало пустым. Это проверка устойчивости к некорректному ответу; фактическое наличие такого значения у реального Omni не установлено.

**Рекомендация:** нормализовать часовой пояс на границе API, при ошибке использовать известное допустимое значение; добавить границу обработки ошибок с восстановлением интерфейса. Расширить проверку схем входящих ответов.

### 4. P2 — штатная навигация может оставлять каталог материалов незагруженным

**Места:** [extension/background.mjs:114](extension/background.mjs#L114), [src/TeachingMaterials.tsx:50](src/TeachingMaterials.tsx#L50), [src/LiveWorkspace.tsx:193](src/LiveWorkspace.tsx#L193).

Обработчик расширения допускает только одну команду чтения одновременно и возвращает `BUSY` для следующей. При этом пользователь может перейти в «Материалы» во время обновления снимка. Монтирование `TeachingMaterials` безусловно запускает запрос каталога, даже при `disabled=true`. Отклонённый запрос не повторяется при завершении обновления. Обратная ситуация также возможна: загрузка каталога не устанавливает общий `busy` родительского компонента.

**Подтверждение:** отдельная проверка обработчика показала `BUSY` для `materials-catalog`, отправленного во время незавершённого `snapshot`; отсутствие ожидания и автоматического повтора установлено по коду. Полный пользовательский сценарий с искусственной задержкой отдельно не прогонялся.

**Рекомендация:** централизовать координацию команд — ограниченная очередь чтения либо отложенная загрузка каталога после освобождения транспорта. Не применять слепые повторы к переключению аккаунта. Добавить тест перехода в раздел во время медленного запроса.

### 5. P2, только desktop — ссылка на оригинал файла блокируется оболочкой

**Места:** [desktop/Program.cs:110](desktop/Program.cs#L110), [src/FilePreview.tsx:68](src/FilePreview.tsx#L68).

Все события `NewWindowRequested` помечаются обработанными без открытия адреса. Между тем «Открыть файл» использует `target="_blank"`. Поэтому предусмотренный интерфейсом запасной путь к оригиналу не реализован в desktop-оболочке; особенно заметно это для неподдерживаемых или слишком больших файлов.

**Основание:** статический анализ обработчика WebView2 и ссылки; запуском desktop не подтверждено. На основной пакет расширения замечание не распространяется.

**Рекомендация:** после проверки допустимости URL открывать оригинал в системном браузере либо реализовать управляемое скачивание. Проверить отдельно от расширения.

## Архитектура и сопровождаемость

**Сильные стороны.** Транспорт скрыт за `omniRequest`; логика расписания, материалов и валидации вынесена в отдельные модули. Включён строгий режим TypeScript для `src`. Есть lock-файлы, CI для модульных тестов и сборки, отдельный workflow с проверкой собранного расширения. README ясно обозначает статус беты и границы режима чтения. Браузерные тесты используют вымышленные данные.

**Основной технический долг.** Контракт команд проверяется во время исполнения, но клиент принимает произвольную строку действия и утверждает тип ответа через generic без проверки схемы. Ключевые `.mjs`-адаптеры не входят в `tsconfig`. Логика получения снимков и обработки сессии частично дублируется между `server/omni-bridge.mjs` и `desktop/omni-agent.mjs`; уже различается обработка challenge-ответов. Крупные компоненты совмещают загрузку, состояние сессии и отображение; JSX записан длинными строками, что затрудняет ревью.

Рациональное направление развития: общий типизированный протокол команд, единая нормализация ответов, контроллер сессии и запросов, затем разделение больших компонентов. Полное переписывание проекта не требуется.

## Безопасность

В расширении положительно реализованы проверка отправителя, ограниченный список команд, проверка разрешённых преподавателей, привязка выполнения к документу вкладки, изолированный контекст чтения, проверка идентичности аккаунта до и после загрузки. Пароль не вводится в интерфейсе расширения. Для превью проверяются адреса, итоговый URL, сигнатуры содержимого и размер; cookies не отправляются.

Критических уязвимостей в проверенном объёме не подтверждено. Это не полноценный пентест. Нулевой результат npm audit не доказывает отсутствие уязвимостей в собственном коде. Главный подтверждённый риск — сохранение старых персональных данных в другой вкладке после смены сессии.

Desktop имеет отдельную модель доверия: интерфейс загружается с GitHub Pages, поэтому его обновление меняет код, имеющий доступ к native bridge. Перед развитием этого варианта стоит предпочесть встроенный версионированный интерфейс. Это архитектурное замечание, а не обнаруженная эксплуатация.

## Производительность и качество поставки

Основной JS-пакет расширения — около 321 КБ, CSS — 45 КБ; PDF загружается отдельно: около 484 КБ кода и 1,27 МБ worker. Для текущего объёма функций это не блокирующая проблема; отложенная загрузка PDF полезна.

Снимок выполняет девять последовательных запросов: два запроса профиля, стартовую информацию и шесть секций. При индивидуальном таймауте 20 секунд время ожидания может приблизиться к трём минутам, блокируя остальные команды. Лучше отделить первичную загрузку профиля от секций, кэшировать редко меняющиеся справочники в пределах сессии и измерить задержки до введения ограниченного параллелизма.

PDF-страницы создаются сразу для всего документа; после первого появления canvas остаётся в памяти. Для длинных документов нужен бюджет памяти или виртуализация. Ограничение скачивания в 8 МБ само по себе не ограничивает объём декодированных изображений и canvas. Нагрузочные измерения в этом ревью не выполнялись.

Расширение проверяется браузерным тестом в Actions, но отдельные workspace/materials/login UI-сценарии в существующие workflows не включены. Нет настроенных lint-проверок, отчёта о покрытии и проверки доступности. Это пробелы процесса, а не доказательство неработоспособности интерфейса. Приоритетнее добавить регрессии для найденных ошибок, чем увеличивать количество поверхностных тестов.

## План доведения до стабильной версии

1. **До следующего выпуска:** синхронизировать смену сессии между вкладками; исправить логотип; валидировать часовой пояс; согласовать конкурирующие запросы. Для каждого исправления добавить проверку воспроизведения.
2. **Следующим этапом:** включить дополнительные UI-сценарии в CI, сохранять диагностику браузерных сбоев, проверить чистую установку и заявленную нижнюю границу браузерной совместимости.
3. **После стабилизации:** объединить протоколы и нормализацию ответов, уменьшить дублирование адаптеров, измерить задержки загрузки и память PDF. Desktop развивать и проверять как отдельный экспериментальный продукт.

Критерий готовности к стабильному выпуску: закрыты замечания 1–4, проходят их регрессии в собранном расширении, объяснена нестабильность браузерного теста и выполнена проверка основных сценариев с разрешённым реальным аккаунтом Omni.
